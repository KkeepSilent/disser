### 0.6. Соглашения по окружению — ВСЕГДА порт 3000

**Правило от заказчика (15.11.2026): сервер всегда поднимается на порту 3000. Новые порты не создавать.**

**Как применять**
- `pnpm dev` → `next dev` (порт 3000 по умолчанию) либо `next dev -p 3000` — **явно**.
- Продакшн-проверка → `next build && next start -p 3000`.
- **Если порт 3000 занят** — сначала освободить его (`Get-NetTCPConnection -LocalPort 3000` → остановить процесс), и только потом стартовать. **Не переходить на 3001/3002/3003/3100** — это ломает единую точку проверки и приводит к тому, что разные запуски проверяют разные сборки.
- Не оставлять в фоне лишние dev-серверы: после проверки — останавливать. (За время ревью накопилось несколько на 3100/3002/3003; они мешают и занимают порты.)
- В отчётах, ТЗ и README указывать единый адрес: **`http://127.0.0.1:3000`**.

**Текущее состояние:** порт 3000 занят процессом `next start` (production-сборка, PID 48696) — это соответствует правилу. Вторые экземпляры не поднимать.

**Файл:** `src/components/Simulator.tsx:26, 34, 38, 43–44`

**Что происходит.** `quantity` берётся из `<input type="number">` без какой-либо валидации. Отрицательное значение принимается, дальше:

```
usedCapital = Σ(trade.quantity * trade.entryPrice)     // строка 34
balance     = Math.max(startingBalance - usedCapital, 0) // строка 38
riskPercent = (riskValue / startingBalance) * 100        // строка 44
```

**Воспроизведение (реальный прогон):** в поле «Размер позиции» ввести `-5`, нажать Buy.

**Фактический результат:**
```
Баланс: $228800      (10000 - (-5 * 43760) = 228800)
Кол-во: -5
Риск:   -2188.00%
```

**Почему это критично.** Все правила наставника в `src/lib/mentor.ts` используют строгое `>`:
- `mentor.ts:15` — `trade.riskPercent > 3` → `-2188 > 3` = false → **«риск выше лимита» не срабатывает**;
- `mentor.ts:39` — `trade.quantity * trade.entryPrice > 5000` → `-218800 > 5000` = false → **«крупная позиция» не срабатывает**.

Проверено: при отрицательном размере наставник выдал только «Нет стоп-лосса» и молчал про баланс $228 800 и риск −2188 %. То есть **вся обучающая логика приложения обходится одной строкой в поле ввода**.

**Что сделать**
- Валидировать `quantity` перед открытием сделки: `Number.isFinite`, `> 0`, шаг `0.01`. При нарушении — не открывать сделку, показывать ошибку под полем, блокировать Buy/Sell.
- Перестать полагаться на атрибут `min="0.01"`: без `<form>` и `required` браузер его не проверяет.
- В `mentor.ts` заменить `>` на осмысленные проверки и добавить правила на «отрицательный/нулевой размер», «риск ≤ 0 %», «размер > X % капитала».
- Защититься от `NaN`/`undefined` во всех полях ввода.

**Критерий приёмки**
- Ввод `-5`, `0`, `abc`, `1e999` не создаёт сделку; под полем появляется понятная ошибка; кнопки заблокированы.
- Риск-правила наставника не обходятся ни одним значением поля.

### 1.2. Короткая позиция (Sell) уменьшает баланс вместо зачисления выручки `[ПРОВЕРЕНО]`

**Файл:** `src/components/Simulator.tsx:34, 38`

**Воспроизведение (реальный прогон):**
1. Buy 0.05 BTC по $43 760 → баланс **$7812** (10000 − 2188).
2. Sell 0.05 BTC по $43 760 → баланс **$5624** (−2188 ещё раз).

**Ожидаемое поведение.** Открытие шорта должно зачислять выручку (баланс 10000 + 2188 = $12 188) и фиксировать короткую позицию, а не списывать номинал.

**Почему это критично.** Номинал long-а и short-а в модели баланса считается одинаково. Это не «неточность», а инвертированная семантика: продажа уменьшает капитал. Всё, что построено поверх (риск в % от капитала, лимит позиции), считается от неверной величины.

**Что сделать.** Выделить модель состояния позиции и разделить:
- **long:** вход списывает `qty × entry`, выход зачисляет `qty × exit`;
- **short:** вход зачисляет `qty × entry`, выход списывает `qty × exit`.

**Критерий приёмки**
- Buy 0.05 → баланс 7812; Sell 0.05 → баланс 12 188; обратный Buy → 7812.
- В журнале видно, что Sell — это шорт, а не «выбытие из лонга».

### 1.3. Нет ограничения маржи: сделка в 44 раза больше депозита проходит молча `[ПРОВЕРЕНО]`

**Файл:** `src/components/Simulator.tsx:38, 143–160`

**Воспроизведение (реальный прогон):** количество `10`, цена $43 760 → номинал **$437 600** при депозите $10 000.

**Фактический результат:**
```
Баланс: $0        ← Math.max(..., 0) зажал отрицательное значение
Сделка: BTC BUY $43760.00  10  $43000.00  76.00%   ← сделка открыта
Ошибка: НЕТ
```

**Почему это критично.** Баланс зажат в ноль через `Math.max`, поэтому система **никогда не сообщает**, что лимит исчерпан. Кнопки Buy/Sell остаются активными — можно открыть сколько угодно позиций «в долг», и всё это в журнале выглядит как нормальные сделки.

**Что сделать**
- Считать доступный капитал (equity) и блокировать сделку, если номинал превышает доступный капитал (для long) / маржу (для short).
- Убрать `Math.max(..., 0)` — вместо тихого зажатия показывать честный equity (включая отрицательный) и причину.
- Кнопки Buy/Sell должны блокироваться, а не выдавать ошибку постфактум.

**Критерий приёмки**
- Количество 10 при депозите $10 000 → сделка не открывается, кнопки `disabled`, видна причина.
- Баланс никогда не показывает `$0` без объяснения.

### 1.4. Баланс на нуле — односторонний храповик, из которого нет выхода `[ПРОВЕРЕНО]`

**Файл:** `src/components/Simulator.tsx:33–38, 40–60, 143–160`

**Воспроизведение (реальный прогон, BTC $43 760):**

| Действие | Баланс | Журнал | Buy/Sell disabled |
|---|---|---|---|
| старт | `$10000` | пусто | false / false |
| Buy 0.25 | `$0` | 1 сделка | false / false |
| Buy 0.25 ещё раз | `$0` | 2 сделки | false / false |
| Sell 0.25 | `$0` | 3 сделки | false / false |

Кнопки `disabled: false` на всём протяжении. Никакого сообщения об ошибке нет.

**Механика (`Simulator.tsx:33–38`):**

```ts
const usedCapital = trades.reduce((sum, t) => sum + t.quantity * t.entryPrice, 0);
const balance = Math.max(startingBalance - usedCapital, 0);   // ← зажимает в ноль
```

**Почему при нуле баланс «не меняется» — четыре наложенные причины:**

1. **`Math.max(..., 0)` прячет отрицательный баланс.** Как только `usedCapital ≥ 10000`, реальное значение (например, −19 400) **никогда не показывается** — пользователь видит ровно `$0` и не понимает, что уже в долгу.
2. **Нет проверки маржи перед сделкой.** `openTrade()` (строки 40–60) вообще не смотрит на `balance`/`usedCapital`. Единственный «предохранитель» — `min="0.01"` у инпута, который без `<form>` не проверяется.
3. **Баланс — чистая функция от номиналов входов, а не от исполнений.** `currentPrice` (строка 31) — всегда закрытие последней свечи и не меняется. Баланс не реагирует ни на цену, ни на закрытие, ни на стоп-лосс. Он меняется **только от факта открытия** сделки.
4. **Односторонний рост `usedCapital`.** Список сделок только растёт: нет закрытия позиции, нет удаления строки, нет кнопки «Новая сессия». Проверено — на странице всего две кнопки: `Buy` и `Sell`.

**Следствие.** Из состояния «баланс $0» **невозможно выйти**:
- Sell не помогает — из-за бага 1.2 шорт тоже **списывает** номинал, а не зачисляет выручку (проверено: Sell 0.25 при балансе $0 дал те же $0);
- уменьшить `usedCapital` нечем — сделки не удаляются;
- единственный выход — **reload**, а он стирает весь журнал и разбор наставника (баг 2.6).

Пользователь попадает в тупик: баланс $0, сделки открываются, интерфейс молчит, прогресс безвозвратно теряется при попытке перезагрузить страницу. Для обучающего продукта это худший возможный сценарий — он учит, что «нормально» торговать без капитала.

**Что сделать**
- Убрать `Math.max(..., 0)`: показывать честный equity (включая отрицательный) либо честный ноль **с причиной** («превышена маржа: −$19 400»).
- Считать **доступный капитал** = equity − зарезервированная маржа, и **блокировать** Buy/Sell, если сделка его превышает (`disabled` + текст причины).
- Перейти на модель позиций (см. 1.2 и 2.9): баланс = cash + стоимость открытых позиций по текущей цене. Тогда баланс реагирует на цену и на закрытие.
- Добавить закрытие позиции (кнопкой и/или автоматически по стопу/тейку) и кнопку «Новая сессия» со сбросом баланса на $10 000.

**Критерий приёмки**
- Попытка открыть сделку сверх капитала: кнопки `disabled`, рядом — причина с цифрой.
- Баланс $0 не может быть достигнут «молча»: либо сделка не проходит, либо виден текст причины.
- Из состояния «$0» есть выход: закрытие позиции возвращает капитал либо «Новая сессия» сбрасывает всё.

## 1A. P0 (новый блок от заказчика) — вход пользователей, CRUD пользователей, персистентный баланс и сделки

**Этот блок добавлен по требованию заказчика и меняет скоуп проекта.** Он отменяет решение Codex из п. 0.1 об удалении Web3-входа: вместо кошелька теперь **логин по паролю**, а роль БД меняется с «декоративной» на «рабочую».

**Итог в одном предложении:** сейчас приложение — это калькулятор риска в памяти вкладки; после блока 1A это должно стать приложением, где у вошедшего пользователя есть **свой ненулевой баланс в Supabase**, а каждая сделка **атомарно** пишется в БД и меняет этот баланс.

### 1A.1. Сейчас входа нет вообще `[ПРОВЕРЕНО]`

**Файлы:** `src/app/page.tsx`, `src/components/*`

**Фактическое состояние:**
- на `/` сразу открывается симулятор — **никакой формы входа, никакой сессии, никакой идентификации пользователя**;
- состояние (журнал, фидбек, баланс) живёт в `useState` компонентов → теряется при reload (п. 2.6);
- `const startingBalance = 10000` (`src/components/Simulator.tsx:22`) — константа в коде, не данные пользователя;
- ни одна таблица Supabase не используется (п. 2.8);
- последняя правка Codex удалила `WalletConnect`/`phantom` → вход в приложение отсутствует в любой форме.

**Что требуется (заказчик):**
1. При заходе на сайт — **логика входа пользователей**.
2. Сейчас достаточно **одного** предварительно настроенного пользователя: **`edu` / `123`**.
3. Пользователи, их баланс и сделки **сохраняются в базе Supabase**, чтобы их можно было **сохранить / изменить / удалить / добавить** через приложение.
4. У пользователя **ненулевой баланс**, чтобы можно было проверять покупку/продажу активов.
5. Кнопки Buy/Sell должны **реально сохранять** сделку и изменить баланс пользователя — не просто пересчитывать локальный стейт.

### 1A.2. Модель пользователей и схема БД

**Файл:** `supabase-schema.sql` (дополнить) либо отдельные миграции `supabase/migrations/`.

```sql
create extension if not exists "pgcrypto";

create table if not exists public.app_users (
  id uuid primary key default gen_random_uuid(),
  username text unique not null check (char_length(username) between 2 and 32),
  password_hash text not null,
  role text not null default 'user' check (role in ('user', 'admin')),
  balance numeric(18, 2) not null default 0 check (balance >= 0),
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

create table if not exists public.app_sessions (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references public.app_users(id) on delete cascade,
  token_hash text not null unique,
  expires_at timestamptz not null,
  created_at timestamptz not null default now()
);

create index if not exists app_sessions_user_id_idx on public.app_sessions(user_id);
create index if not exists app_sessions_expires_at_idx on public.app_sessions(expires_at);
```

**Требования к таблице пользователей**
- `password_hash` — **только хэш**, пароль в открытом виде не хранится нигде (в БД, в логах, в git).
- Хэширование — на сервере. Рекомендуется `pgcrypto`: `crypt(password, gen_salt('bf'))` (bcrypt), либо Node `crypto.scrypt`. **Недопустимо** `md5`/`sha1`/`sha256(password)` без соли.
- `balance` — деньги пользователя, `numeric`, **не ноль** (см. 1A.4).
- `role` — `admin` для `edu` (ему доступно управление пользователями), `user` для остальных.
- `updated_at` — обновлять триггером или в каждом UPDATE.

**Требования к таблице сессий**
- Хранить **не сам токен**, а его хэш (`sha256` токена — здесь допустимо, токен случайный и высокоэнтропийный).
- `expires_at` — TTL (например, 7 дней) + «продлить» при активности.
- `on delete cascade` — удаление пользователя чистит его сессии и сделки.

**Доработка `public.trades`** (таблица уже есть в `supabase-schema.sql`, но не используется):

```sql
alter table public.trades
  add column if not exists user_id uuid references public.app_users(id) on delete cascade,
  add column if not exists scenario_id text,
  add column if not exists status text not null default 'open' check (status in ('open','closed','cancelled')),
  add column if not exists exit_price numeric,
  add column if not exists realized_pnl numeric,
  add column if not exists closed_at timestamptz;
```

### 1A.3. Вход: единственный пользователь `edu` / `123`

**Требования**
- На `/` (или на `/login`) — **форма входа**: логин + пароль.
- Пока пользователь не вошёл — **симулятор недоступен** (страница-гейт, а не просто спрятанная кнопка).
- Кнопки Buy/Sell, поля размера позиции и стопа **неактивны** без сессии.
- Пароль `123` проверяется против `password_hash` в `app_users`.
- Есть **«Выйти»**: сессия удаляется, пользователь возвращается на форму входа.
- Сессия переживает reload и перезапуск dev-сервера.
- Неверный логин/пароль — понятное сообщение, без утечки, какое именно поле неверно.

**Сессия — только httpOnly cookie**
- `HttpOnly` + `SameSite=Lax` + `Secure` (в проде) — JS не должен читать токен.
- **Нельзя** хранить токен в `localStorage` (доступен из XSS) — это требование безопасности, не вкусовое.

**Обязательно:** сначала проверить, что пользователь существует, **и только потом** сравнивать пароль, и сравнение делать **константным по времени** (`crypt` из pgcrypto это умеет). Иначе по времени ответа можно перебирать существующие логины.

### 1A.5. Сделки и баланс сохраняются в БД — атомарно

**Это ключевое требование заказчика:** «активация кнопок … Buy/Sell … должна присутствовать логика сохранения сделок/баланса пользователя».

**Клиентский `onClick` → `fetch('/api/trades', …)` → Postgres-функция → обновлённое состояние.** Никаких локальных пересчётов баланса как источника истины.

**Правило: запись сделки и изменение баланса — одна транзакция.** Реализовать Postgres-функцией (RPC) с `security definer`:

```sql
create or replace function public.place_trade(
  p_user_id uuid,
  p_scenario_id text,
  p_asset text,
  p_side text,
  p_entry numeric,
  p_quantity numeric,
  p_stop numeric default null,
  p_risk_percent numeric default 0
) returns public.trades
language plpgsql
security definer
set search_path = public
as $$
declare
  v_user public.app_users;
  v_notional numeric;
  v_delta numeric;
  v_trade public.trades;
begin
  if p_side not in ('buy','sell') then raise exception 'invalid side'; end if;
  if p_quantity is null or p_quantity <= 0 then raise exception 'quantity must be positive'; end if;
  if p_entry is null or p_entry <= 0 then raise exception 'entry price must be positive'; end if;

  select * into v_user from public.app_users where id = p_user_id for update;
  if not found then raise exception 'user not found'; end if;

  v_notional := p_quantity * p_entry;

  -- long: вход списывает номинал; short: вход зачисляет выручку (см. п. 1.2)
  if p_side = 'buy' then
    v_delta := -v_notional;
    if v_user.balance < v_notional then
      raise exception 'insufficient funds: need %, available %', v_notional, v_user.balance;
    end if;
  else
    v_delta := v_notional;
    -- для шорта требуется обеспечение: номинал не должен превышать капитал
    if v_user.balance < v_notional then
      raise exception 'insufficient margin: need %, available %', v_notional, v_user.balance;
    end if;
  end if;

  insert into public.trades (user_id, scenario_id, asset_symbol, side, entry_price, quantity, stop_loss, risk_percent)
  values (p_user_id, p_scenario_id, p_asset, p_side, p_entry, p_quantity, p_stop, p_risk_percent)
  returning * into v_trade;

  update public.app_users
     set balance = balance + v_delta, updated_at = now()
   where id = p_user_id;

  return v_trade;
end;
$$;

revoke execute on function public.place_trade(uuid, text, text, text, numeric, numeric, numeric, numeric) from public, anon, authenticated;
```

**Почему именно так (это чинит сразу несколько пунктов ТЗ):**
- проверка капитала и запись — **в одной транзакции** → состояние не может разъехаться;
- `for update` — блокировка строки, два параллельных клиента не могут списать баланс дважды;
- `raise exception` → транзакция откатывается → **сделка не пишется, если денег нет** (то есть баги 1.1–1.4 закрываются на уровне данных, клиент не может обойти проверку, даже вызвав REST напрямую);
- проверка `p_quantity > 0` на сервере БД закрывает баг 1.1 на уровне данных;
- `revoke execute ... from public, anon` — иначе функцию с `security definer` сможет вызвать **любой**, у кого есть anon-ключ, и вызвать её от чужого `p_user_id`.

**Аналогично** нужна функция закрытия позиции:

```sql
create or replace function public.close_trade(p_trade_id uuid, p_exit numeric)
returns public.trades
language plpgsql
security definer
set search_path = public
as $$
declare
  v_trade public.trades;
  v_user public.app_users;
  v_pnl numeric;
  v_cash numeric;
begin
  select * into v_trade from public.trades where id = p_trade_id for update;
  if not found then raise exception 'trade not found'; end if;
  if v_trade.status <> 'open' then raise exception 'trade is not open'; end if;

  select * into v_user from public.app_users where id = v_trade.user_id for update;

  -- P&L: long растёт с ценой, short падает
  if v_trade.side = 'buy' then
    v_pnl := (p_exit - v_trade.entry_price) * v_trade.quantity;
  else
    v_pnl := (v_trade.entry_price - p_exit) * v_trade.quantity;
  end if;

  v_cash := case when v_trade.side = 'buy' then p_exit * v_trade.quantity else -p_exit * v_trade.quantity end;

  update public.trades
     set status = 'closed', exit_price = p_exit, realized_pnl = v_pnl, closed_at = now()
   where id = p_trade_id;

  update public.app_users
     set balance = balance + v_cash + v_pnl, updated_at = now()
   where id = v_trade.user_id;

  return v_trade;
end;
$$;
```

**Правила безопасности (обязательны, иначе получится дыра):**
- `SUPABASE_SERVICE_ROLE_KEY` — **только сервер**, переменная **без** префикса `NEXT_PUBLIC_`, никогда не попадает в клиентский бандл. Проверить по бандлу после сборки (см. п. 3.10).

- Пароль хэшируется **на сервере**, никогда не логируется и не возвращается в ответе.
- Не отдавать наружу `password_hash` даже админу.
- `DELETE /api/users/:id` — нельзя удалить самого себя (админа), иначе можно потерять единственный доступ.
- Роли проверяются на сервере по данным сессии, а не по тому, что прислал клиент.

### 2A.1. P&L по любой сделке равен нулю — закрытие позиции не может дать прибыль или убыток `[ПРОВЕРЕНО]`

**Файлы:** `src/app/api/trades/[id]/close/route.ts:22–23`, `src/app/api/trades/route.ts:96`

```ts

// выход
const exitPrice = scenario?.candles.at(-1)?.close;
```

**Оба берут цену из одной и той же точки — закрытия последней свечи.** Значит `exit === entry` всегда, и `realized_pnl = (exit − entry) × qty ≡ 0`.

**Проверка вживую:** открыл шорт 0.05 BTC по $43 760 со стопом $44 000, нажал «Закрыть» → в журнале `SELL · BTC  $43760.00 → $43760.00`, результат **«+$0.00»**, баланс вернулся ровно к $18 436.

**Почему это критично.** Механизм P&L написан и работает, но он **физически не может** дать ненулевой результат. Пользователь закрывает позицию и всегда получает ноль — обучение теряет смысл: закрыть позицию по стопу и увидеть убыток невозможно. Это прямое следствие п. 2.3 (цена не двигается).

**Что сделать** — как только появится движение цены (2.3), выход должен брать **текущую** цену, а не последнюю свечу сценария. Дополнительно: при движении цены закрывать позиции автоматически при достижении стопа/тейка, а не только по кнопке.

**Критерий приёмки**
- Закрытие по цене, отличной от входа, даёт ненулевой P&L; баланс пересчитывается по формуле из 1A.5.
- Срабатывание стоп-лосса фиксирует убыток и записывает его в `trades.realized_pnl`.

### 2B.2. Рынок едет 5.4–6.4 секунды на одну свечу `[ПРОВЕРЕНО]`

**Замер (реальный прогон, нажатие «Следующая свеча»):**

| Замер | Время |
|---|---|
| 1-е нажатие | **6 193 мс** |
| 2-е | **5 439 мс** |
| 3-е | **6 420 мс** |
| 4-е | **5 690 мс** |

**Прямые замеры API (из вкладки):**

| Запрос | Время |
|---|---|
| `GET /api/auth/me` | **1 427 мс** |
| `GET /api/trades?scenario_id=…` | **2 392 мс** |

**Почему так медленно — четыре сложенные причины:**

1. **Одно нажатие = три HTTP-запроса подряд.** `advanceCandle()` (строка 209) → `POST /api/simulations/advance`, затем `refreshFromServer()` → `GET /api/trades` + `GET /api/auth/me`. Итого ≈ 1.5 + 2.4 + 1.4 ≈ **5.3 с** — совпадает с измерением.
2. **Каждый запрос к API делает 3 последовательных запроса к БД.** `readSessionUser()` (`lib/server/auth.ts:63–105`): SELECT сессии → SELECT пользователя → **UPDATE сессии** (продление `expires_at`) — и это на *каждом* запросе, включая `extend: true` из `getRequestUser()`.
3. **В `GET /api/trades` есть дублирующий запрос.** Строки 17–25 уже выбирают `"id, current_candle_index"`, но строки 59–67 **повторно** запрашивают `current_candle_index` у той же сессии. Первый результат в переменной `session` не переиспользуется — значение `current_candle_index` из него выбрасывается.
4. **N+1 в `advance`:** на каждую открытую позицию — отдельный `close_trade` RPC (строка 71), плюс отдельные SELECT'ы за позициями и за балансом. При 5 открытых сделках это +10 сетевых round-trip'ов.

**Дополнительно:** база — удалённый Supabase, поэтому каждый round-trip ≈ 300–700 мс.

**Что сделать**
- **Убрать дублирующий запрос** в `api/trades/route.ts` (строки 59–67) — переиспользовать `session.current_candle_index` из первого SELECT'а.
- **Не продлевать сессию на каждом запросе** — обновлять `expires_at`, только если осталось меньше суток (или раз в час).
- **Кэшировать профиль пользователя** в сессии (в `app_sessions` добавить `username`/`role`/`balance_snapshot`) либо мемоизировать на уровне запроса; сейчас профиль читается из БД при каждом обращении.
- **Объединить `/api/trades` и `/api/auth/me`** в один ответ (баланс уже есть в ответе `/api/trades` — строка 81 возвращает `balance`! То есть второй запрос **дублирует** первый).
- **Отдавать баланс из ответа `advance`** (он уже возвращается, строка 92) и **не делать повторный `refreshFromServer`** после advance — вместо этого обновлять состояние из ответа.
- Вынести проверку стоп-лоссов в **одну** SQL-функцию вместо цикла с RPC на каждую позицию.

**Критерий приёмки**
- Одно нажатие «Следующая свеча» → обновление графика **≤ 1.5 с** на dev-окружении.
- `GET /api/trades` → **≤ 800 мс**.
- Количество сетевых запросов к Supabase на одно нажатие — **≤ 3** (вместо ~14 сейчас).

### 2B.6. Гард «цена изменилась» в БД мёртвый `[ПРОВЕРЕНО чтением]`

**Файлы:** `src/app/api/trades/route.ts:123–138`, `supabase-schema.sql:299`

В `place_trade` есть защита:
```sql
if v_session.current_candle_index <> p_candle_index then
  raise exception 'simulation price changed; refresh before opening a trade';
```

Но API **не берёт индекс из запроса** — он читает `current_candle_index` из той же сессии и передаёт его в RPC:
```ts
const candleIndex = Math.min(Math.max(Number(session.current_candle_index) || 0, 0), …);
…
p_candle_index: candleIndex
```
Сравнение `session.current_candle_index <> p_candle_index` — **тавтология**, оно никогда не сработает. Клиент (`Simulator.tsx:148`) индекс свечи вообще не отправляет.

**Почему это важно.** Реальный сценарий рассинхрона: у клиента `candleIndex = 3` (цена $X), а в БД сессия уже на 5 (цена $Y) — например, вторая вкладка, или `refreshFromServer` упал, а ошибка ушла в `setError`. Тогда:
- клиент валидирует стоп по **своей** цене ($X) — `buyStopError` может не сработать;
- сервер записывает вход по **своей** цене ($Y) и отвергает стоп с 400 «Для Buy стоп-лосс должен быть ниже цены входа» — **непонятная ошибка**;
- либо, если стоп проходит, сделка откроется по цене, которой пользователь не видел.

**Что сделать**
- Клиент отправляет `candle_index` в `POST /api/trades`.
- API сверяет присланный индекс с `session.current_candle_index`; при расхождении — `409` с текстом «Рынок изменился, обновите страницу».
- RPC-гард оставить (тогда он станет рабочим).

**Критерий приёмки**
- При рассинхроне индексов сделка **не создаётся**, пользователь получает понятное сообщение.

### 2C.1. Линия стоп-лосса исчезает с графика `[ПРОВЕРЕНО — критично, регресс]`

**Файл:** `src/components/Simulator.tsx:66, 384–403`

```ts

// getChartScale: values = только low/high свечей
const values = candles.flatMap((candle) => [candle.low, candle.high]).filter(Number.isFinite);
```

**Что произошло.** В прошлой версии домен оси Y считался как `priceBounds`, куда **входили** `entry_price` и `stop_loss` открытых позиций. Теперь `getChartScale()` смотрит **только на свечи сценария** — про открытые позиции не знает.

**Воспроизведение (реальный прогон, ETH):**
1. Цена $1 908.92, ось Y = `1,890 / 1,900 / 1,910 / 1,920 / 1,930` (видимый диапазон ≈ $1 880–1 940).
2. Поставил стоп **$1 813.47** (5 % ниже цены) — валидный, сервер принял сделку.
3. Журнал: `BUY · ETH  $1908.92  0.479  $1813.47  0.25%  Открыта` — всё верно.
4. **На графике `refLinesInDom: 2`** — только «Сейчас» и «Вход BUY». Метки «Стоп» в DOM **нет вообще**: Recharts не рисует `ReferenceLine` за пределами домена.

**Почему это критично.** Реальный стоп на 5 % ниже цены **невозможно увидеть на графике** — свечи 15 минут почти всегда укладываются в ±0.5 %, а стоп игрока стоит за пределами этого коридора. Пользователь ставит стоп, не видит его и не может оценить, где риск. Вся фича «линия стопа на графике», добавная в прошлой итерации, в реальных данных **не работает**.

**Что сделать**
- Вернуть в домен оси значения открытых позиций: `entry_price` и `stop_loss` (и текущую цену).
- Но тогда нельзя просто расширять домен: стоп в 5 % от цены растянет свечи в нечитаемую полосу. Правильный подход — **два варианта отображения**:
  - либо домен = max(свечи, позиции) и на графике появляется зона «стоп»;
  - либо ось Y остаётся по свечам, а стоп рисуется **отдельным маркером у нижней границы с подписью «Стоп $1 813 (вне диапазона)»**.
- Минимум: если стоп вне домена, всё равно показать его числом в подписи/легенде.

**Критерий приёмки**
- При любом стопе (в пределах и вне диапазона свечей) пользователь видит на графике, где стоит стоп и насколько далеко он от цены.

### 2D.1. Что сейчас не так `[ПРОВЕРЕНО]`

**Проверка кода:** в клиенте (`src/components/*.tsx`, `src/app/**/*.tsx`) **нет ни одного** `setInterval`, `setTimeout`, `EventSource`, `WebSocket` или поллинга — 0 совпадений. Цена меняется **исключительно** по нажатию «Следующая свеча».

**Проверка в браузере:** подключение к Binance WS — `ok: true`, 8 событий за ~2 с, `bookTicker` отдаёт мгновенную цену; REST `klines` отдаёт меняющуюся формирующуюся свечу (volume 0.06672 → 0.07296 за несколько секунд). То есть **live-режим технически доступен бесплатно и без ключа** — текущая реализация просто выбрала другой путь.

**Почему текущую модель нельзя «просто ускорить»** — весь стек построен на снимке:

| Слой | Сейчас | Что требуется для live |
|---|---|---|
| Источник данных | `simulation_sessions.candles` (jsonb, 8 свечей) | поток котировок |
| Движение цены | `current_candle_index + 1` по кнопке | push-обновления, тики |
| Цена входа | `candles[expected_candle_index].close` (`api/trades/route.ts:145`) | текущая цена на момент клика, **с сервера** |
| Проверка стопа | на «следующей» свече снимка (`advance_simulation_session_atomic`) | на **каждом** обновлении цены |
| P&L | при закрытии, по цене из снимка | mark-to-market в реальном времени + нереализованный P&L |
| Метрика «Рыночное время» | `10:45 · 5/8` — порядковый номер свечи в снимке | реальное время + индикатор Live |
| Завершение сценария | `marketFinished` → торговля блокируется (`Simulator.tsx:83–84`) | не существует |

**Проблема обучения, которую надо решить явно.** Сценарии «Ложный пробой» и «Паническая распродажа» — это **смоделированные** рыночные ситуации. На живом случайном рынке они не воспроизводятся. Поэтому нужен **двойной режим** (см. 2D.6), а не просто замена кнопки на таймер.

### 2D.2. Источник котировок в реальном времени

**Основной — WebSocket, напрямую из браузера** (проверено, работает, без ключа, CORS к WS не применяется):

```
wss://stream.binance.com:9443/stream?streams=btcusdt@kline_1m/ethusdt@kline_1m/solusdt@kline_1m
wss://stream.binance.com:9443/ws/btcusdt@bookTicker     ← мгновенная цена bid/ask
```

**Требования**
- Подписка **только на текущий актив** (не на все три) + переподписка при смене сценария.
- `bookTicker` — мгновенная цена (тики ~каждую секунду). `kline_1m` — свечи; **формирующаяся** свеча меняет open/high/low/close до закрытия интервала.
- На закрытии интервала добавляется новая свеча в график, предыдущая фиксируется.
- Хранить в клиенте не более ~120 свечей, старые подрезать.
- **Переподключение**: при обрыве — экспоненциальный backoff (1 с → 2 → 4 → 8 с, максимум 30 с), индикатор «соединение потеряно».
- **Реконнект при возврате вкладки** (`visibilitychange`) и при смене актива.

**Fallback (обязателен)** — Binance API недоступен из части регионов и иногда блокирует IP:
- REST-поллинг через серверный Route Handler `GET /api/market/tick?asset=BTC` → внутри `GET https://api.binance.com/api/v3/klines?symbol=BTCUSDT&interval=1m&limit=2`, раз в 3 с, с кэшем 1–2 с на сервере.
- Если и REST недоступен — CoinGecko (`/api/v3/simple/price`) или Kraken public API (`https://api.kraken.com/0/public/Ticker`).
- В UI честно показывать текущий источник: «Binance WS» / «Binance REST (3 с)» / «резервный источник» / «нет данных».

**Ограничения, которые надо учесть**
- Binance REST: 1200 req/min на IP → при серверной подписке на всех пользователей хватает с запасом, при клиентском WS — нагрузки на сервер нет вообще.
- CoinGecko: ~10–30 req/min → только для fallback с кэшем 30–60 с.
- Данные Binance — USDT-пары; курс USDT≈USD допустим для MVP, но это стоит написать в README.

### 2D.3. Автообновление в интерфейсе

**Требования**
- Цена в метрике «Цена» обновляется на каждом тике (не реже 1 раза в секунду) без участия пользователя.
- График: последние N закрытых свечей + **формирующаяся** свеча, которая двигается в реальном времени; при закрытии интервала новая свеча добавляется сама.
- Ось Y пересчитывается на лету, с теми же «человеческими» шагами (`getChartScale`).
- **Кнопка «Следующая свеча» в live-режиме отсутствует.** Вместо неё — индикатор состояния соединения.
- Индикатор: «● Live · Binance · обновлено 12:04:37» (пульсирующая точка). При обрыве: «○ нет соединения · последняя цена от 12:03:02» + кнопка «Переподключиться».
- Пересчёт метрик (equity, нереализованный P&L, расстояние до стопа/тейка) — **на клиенте** из последней цены, без запросов в БД.

### 2D.4. Модель позиций для живого рынка

**Что меняется в БД и логике**

1. **Вход по текущей цене.** `place_trade` должен брать цену **с сервера** (из live-фида), а не из снимка. Нужен серверный singleton с текущей ценой (см. 2D.5) — иначе клиент пришлёт цену, которой нет.
2. **Гард свежести вместо гарда индекса.** Клиент шлёт `expected_price`; сервер сверяет со своей live-ценой. Расхождение > 0.5 % → `409 «Цена изменилась, повторите»`. Текущий `expected_candle_index` в live-режиме теряет смысл.
3. **Стоп-лосс проверяется на каждом обновлении цены**, а не «на следующей свече». Значит проверку нужно вынести из `advance_simulation_session_atomic` (он вообще больше не нужен) в поток обновления цены.
4. **Mark-to-market.** Разделить:
   - `balance` — **кэш** (деньги), меняется только при открытии/закрытии;
   - `equity` — `balance + Σ(qty × (price − entry))` для лонга и `balance + Σ(qty × (entry − price))` для шорта; показывается в реальном времени, в БД не пишется.
5. **Нереализованный P&L по каждой открытой позиции** — в журнале колонкой, обновляется на клиенте.
6. **Расстояние до стопа/тейка**: «до стопа −2.3 % / −$42.10» — пересчитывается на каждом тике.
7. **Тейк-профит** — добавить как необязательное поле (сейчас есть только стоп).

### 2D.5. Где живёт «живая цена» и кто проверяет стопы

**Проблема:** проверять стопы на каждом тике значит на каждом тике ходить в БД. При 1 тике/сек и N пользователях это лавина.

**Решение — серверный singleton-подписчик:**
- Один процесс держит **одно** WS-подключение к Binance на все активы (1 соединение на сервер, а не на пользователя).
- Текущая цена каждого актива кэшируется в памяти сервера.
- Отдельный тик (раз в 1–2 с) проверяет **все открытые позиции всех пользователей** на пробой стопа и закрывает их одной транзакцией (переиспользовать логику `close_trade` из `advance_simulation_session_atomic`).
- Клиент получает цену из `/api/market/tick` (раз в 1–3 с) **или** по SSE от того же сервера.

**Почему так, а не «клиент шлёт цену на каждый тик»:**
- один запрос от клиента = одна транзакция проверки на пользователя → нагрузка растёт с числом пользователей;
- singleton делает **O(1) проверок на тик независимо от числа пользователей**;
- сервер проверяет стопы даже когда вкладка закрыта — сейчас стоп срабатывает **только** если пользователь сидит на странице и жмёт кнопку, что для живого рынка неприемлемо.

**Следствие:** стоп-лосс должен срабатывать и при закрытой вкладке. Значит нужен **long-running процесс** (Node-сервер с `setInterval`), а не serverless-деплой. Это надо зафиксировать в README как требование к хостингу.

**Альтернатива попроще**, если singleton не хочется: проверять стопы **по запросу клиента** — раз в 2–3 с клиент шлёт свою цену, сервер сверяет с открытыми позициями. Проще, но: (а) нагрузка растёт с пользователями, (б) стоп не сработает при закрытой вкладке. Допустимо для MVP, но оговорить ограничение явно.

### 2D.6. Два режима: «Реальный рынок» и «Учебный сценарий»

**Проблема, которую нельзя игнорировать:** «Ложный пробой» и «Паническая распродажа» — **сценарии**, т.е. смоделированные последовательности свечей. На живом рынке их не бывает. Если просто заменить кнопку на таймер, обучающая часть приложения перестанет работать.

**Предлагаемая модель** — переключатель в шапке симулятора:

| | **Реальный рынок** (по умолчанию) | **Учебный сценарий** |
|---|---|---|
| Данные | live-поток Binance | снимок 8 свечей из `scenarios.ts` |
| Движение | автоматически, тики | автоматически, 1 свеча каждые N секунд (**автоплей**) |
| Сценарий | реальный рынок | «Растущий рынок» / «Ложный пробой» / «Паническая распродажа» |
| Стоп-лосс | на каждом тике | на каждой автопрогрессированной свече |
| Обучение | риск-менеджмент на живых данных | разбор конкретных рыночных ситуаций |

**Автоплей в учебном режиме** — то, чего сейчас нет вообще: свеча сама продвигается каждые N секунд (N настраивается: 1 с / 3 с / 10 с / 30 с), с индикатором «автоплей: 3 с». Кнопка «Следующая свеча» остаётся как ручной шаг (для отладки), но не как основной способ.

**Второй сценарий на тех же данных:** «учебный» режим может использовать **реальные** последние 8 свечей выбранного актива как снимок (с реальными ценами) — тогда он не будет врать про котировки. Собственные `scenarios.ts` остаются для двух «специальных» рыночных ситуаций.

### 2D.9. Критерии приёмки

- [ ] Цена обновляется **автоматически** без нажатия кнопок, не реже 1 раза в секунду
- [ ] График сам пополняется новыми свечами; формирующаяся свеча двигается в реальном времени
- [ ] Кнопка «Следующая свеча» в live-режиме отсутствует; есть индикатор Live и время последнего обновления
- [ ] При обрыве соединения — явная индикация + автопереподключение с backoff + ручная кнопка
- [ ] Есть работающий fallback, если WS недоступен (REST-поллинг), и это видно в UI
- [ ] Вход в сделку фиксирует **текущую** цену; расхождение с ценой на экране > 0.5 % → `409` с понятным текстом
- [ ] Стоп-лосс срабатывает автоматически при достижении уровня — **в том числе при закрытой вкладке**
- [ ] Equity и нереализованный P&L пересчитываются в реальном времени; баланс (кэш) меняется только на открытии/закрытии
- [ ] Учебный режим с автоплеем сохранён и доступен переключателем
- [ ] Никаких запросов в БД на каждый тик (тик не пишет в БД; в БД пишутся только открытие/закрытие сделки)

## 2E. P1 — график должен быть свечным, а не сглаженным сплайном (требование заказчика)

**Требование (14.11.2026):** «посмотри какой он гладкий, так же не бывает» — приложен скриншот TradingView по BTCUSDT. Приложение рисует `AreaChart` с `type="monotone"` — гладкую кривую через `close`. На реальной бирже — **японские свечи**: тело (open→close) + фитиль (low→high), плюс объём.

### 2E.1. Что не так сейчас `[ПРОВЕРЕНО]`

**Файл:** `src/components/Simulator.tsx:296–308`

```tsx
<AreaChart data={visibleCandles}>
  <Area dataKey="close" fill="url(#price)" stroke="#49627a" strokeWidth={3} type="monotone" />
</AreaChart>
```

**Сравнение с TradingView (по приложенному скриншоту):**

| Что | TradingView | Приложение сейчас |
|---|---|---|
| Элемент графика | свечи: тело + фитиль | сглаженный Area-сплайн по `close` |
| High/low | фитиль рисует полный диапазон | **не рисуется** — данные есть, но не используются |
| Open/close | тело свечи (зелёная/красная) | **не рисуется** — только `close` |
| Цвет | зелёный (close ≥ open) / красный (close < open) | один синий цвет у всех свечей |
| Объём | гистограмма внизу, цвет свечи, прозрачность | **не рисуется** — данные есть, но не используются |
| Ось цены | **справа**, много делений | слева, 4–5 делений |
| Метка текущей цены | зелёный бокс на оси: `67 326,00` + `09:41` + `67 292,00` | нет |
| Легенда OHLC | `ОТКР / МАКС / МИН / ЗАКР / +137,73 (+0,20%)` сверху | только в тултипе |

**Почему это важно именно для обучения.** `type="monotone"` рисует **не существующую в рынке траекторию**: реальная цена прыгает от закрытия одной свечи к открытию следующей, а сплайн рисует плавную дугу между ними. Новичок, обучающийся на таком графике, формирует неверное представление о том, как распределяется риск внутри свечи и насколько «гладким» бывает рынок. Кроме того, `high`/`low` уже скачиваются из Binance (`market-data.ts:40–41`), но **не используются** — половина данных лежит без дела.

**Данные для отрисовки уже есть.** Тип `Candle` (`src/lib/types.ts`) содержит `open/high/low/close/volume`, и `market-data.ts` их заполняет из Binance. Менять получение данных не нужно — нужен только рендер.

### 2E.2. Рецепт свечей в Recharts — проверен на этом проекте

В Recharts нет готового свечного графика, но есть рабочий приём: **`Bar` со значением-диапазоном `[low, high]` + кастомная `shape`**, которая рисует фитиль и тело. Проверено на живом проекте (временный роут, DOM-замеры):

```tsx
const data = candles.map((candle) => ({ ...candle, range: [candle.low, candle.high] }));

type CandleShapeProps = {
  x?: number; y?: number; width?: number; height?: number;
  payload?: { open: number; close: number; high: number; low: number; range: [number, number] };
};

function Candle({ x = 0, y = 0, width = 0, height = 0, payload }: CandleShapeProps) {
  if (!payload) return null;
  const { open, close, high, low, range } = payload;
  const [rangeLow, rangeHigh] = range;
  const span = rangeHigh - rangeLow || 1;
  // y — верх диапазона, height — высота диапазона в пикселях
  const toPx = (value: number) => y + ((rangeHigh - value) / span) * height;
  const isUp = close >= open;
  const color = isUp ? "#0d9e6f" : "#e04b45";
  const bodyTop = toPx(Math.max(open, close));
  const bodyBottom = toPx(Math.min(open, close));
  const bodyHeight = Math.max(bodyBottom - bodyTop, 1);
  const center = x + width / 2;
  const bodyWidth = Math.max(width * 0.62, 1);
  return (
    <g>
      <line x1={center} x2={center} y1={toPx(high)} y2={toPx(low)} stroke={color} strokeWidth={1} />
      <rect x={center - bodyWidth / 2} y={bodyTop} width={bodyWidth} height={bodyHeight} fill={color} />
    </g>
  );
}
```

**Использование:**
```tsx
<ComposedChart data={data} margin={{ top: 8, right: 64, bottom: 8, left: 0 }}>
  <CartesianGrid stroke="#e5e0d5" strokeDasharray="3 3" />
  <XAxis dataKey="time" axisLine={false} tickLine={false} />
  <YAxis yAxisId="price" orientation="right" domain={chartScale.domain} ticks={chartScale.ticks} width={60} />
  <YAxis yAxisId="volume" hide domain={[0, maxVolume * 4]} />
  <Tooltip content={<CandleTooltip />} />
  <Bar yAxisId="price" dataKey="range" shape={<Candle />} isAnimationActive={false} />
  <Bar yAxisId="volume" dataKey="volume" shape={<VolumeBar />} isAnimationActive={false} />
</ComposedChart>
```

**Замеры из DOM (реальный прогон, 4 свечи):**
```
свечей: 4,  фитилей (line): 4,  тел (rect): 4
10:00  open 100 close 105 → fill #0d9e6f (зелёная),  rect y=53  h=80, line y1=37  y2=149
10:15  open 105 close 102 → fill #e04b45 (красная),   rect y=53  h=48, line y1=21  y2=117
10:30  open 102 close 96  → fill #e04b45 (красная),   rect y=101 h=96, line y1=69  y2=213
10:45  open  96 close 98  → fill #0d9e6f (зелёная),  rect y=165 h=32, line y1=149 y2=245
```
Пиксельная математика сходится точно: `toPx(v) = y + (rangeHigh − v) / (rangeHigh − rangeLow) × height`.

**Объём — отдельная ось.** `domain={[0, maxVolume * 4]}` заставляет гистограмму занимать нижние ~25 % высоты (TradingView делает то же самое). Замер: объёмы 12/30/44/21 → высоты 17/43/63/30 px, `fillOpacity={0.45}`, цвет — по направлению свечи.

**Важно:** `isAnimationActive={false}` — иначе свечи «вырастают» при каждом обновлении.

### 2E.3. Что должно быть на графике

**Обязательно**
1. **Свечи**: тело open→close (зелёная `#0d9e6f` / красная `#e04b45`), фитиль low→high, ширина тела ~60 % от слота.
2. **Объём** в нижней панели (~25 % высоты), цвет свечи, прозрачность ~45 %.
3. **Ось цены справа** (`orientation="right"`, `margin.right` ≈ 64) — как на TradingView, а не слева.
4. **Метка текущей цены на оси**: цветной бокс с ценой (`67 326,00`) + под ним время и последнее закрытие. Реализуется через кастомный `label` у `ReferenceLine` (проверено: текст рендерится) либо через отдельный слой поверх графика.
5. **Линия текущей цены** — пунктирная, на уровне последнего `close`.
6. **Линии входа и стопа** — оставить, но теперь они рисуются поверх свечей (`ReferenceLine`), и их **обязательно** надо включать в домен оси (см. 2C.1 — сейчас они исчезают за пределами диапазона).

### 2F.1. Свечи сдавлены стоп-лоссом в 6 % высоты графика `[ПРОВЕРЕНО — критично]`

**Файл:** `src/components/Simulator.tsx` — `getChartScale(candles, currentPrice, openTrades)`

```ts
const positionLevels = openTrades.flatMap((trade) => [
  Number(trade.entry_price),
  ...(trade.stop_loss === null ? [] : [Number(trade.stop_loss)])
]);
const values = [...candles.flatMap((c) => [c.low, c.high]), currentPrice, ...positionLevels]
```

**Что произошло.** Codex выполнил 2C.1 буквально: добавил `entry_price` и `stop_loss` в домен оси безусловно. Побочный эффект — **ценовое действие перестало быть читаемым**.

**Воспроизведение (реальный прогон, BTC):**
```
Цена $65 496.98, свечи в диапазоне 65 409…65 677   (размах 0,4 %)
Стоп $62 222.13                                     (5 % ниже цены)
→ домен оси: 60 000 … 66 000                       (размах 10 %)
→ свечи заняли ~15 px из ~255 px высоты поля       (6 %)
```
На скриншоте свечи выглядят как тонкие полоски у верхней границы, объём — гигантские столбцы внизу, объём явно доминирует, и цену невозможно читать. То есть **2C.1 формально закрыт, а пользовательский смысл сломан**: приложение стало нечитаемым ровно тогда, когда у игрока есть стоп (то есть почти всегда).

**Что сделать — clamp вместо безусловного включения**

Правило: домен оси строим по **свечам и цене**, а уровни позиций добавляем **только если они близко** к диапазону:

1. `entry_price` — всегда включать (он по определению рядом с текущей ценой, иначе сделка была бы невозможна).
2. `stop_loss` — включать в домен, **только если** он отличается от границы диапазона свечей не более чем на **X % (например, 1 %)** от текущей цены. Иначе стоп **не расширяет домен**, а рисуется как маркер у края:
   - горизонтальная пунктирная линия у нижней (или верхней) границы поля;
   - подпись вида `↓ 62 222 (−5,0 %)` — чтобы было видно, что уровень ниже видимой области.
   - То же для тейк-профита, когда он появится.
3. Альтернатива (если нужен «честный» масштаб) — **отдельная вторая панель** для уровней позиций, как в некоторых терминалах.

**Критерий приёмки**
- При стопе в 5 % от цены свечи занимают **не менее 60 %** высоты поля; стоп при этом виден (линия у края + подпись с уровнем и расстоянием в %).
- При стопе в пределах 1 % стоп рисуется обычной линией внутри поля.

### 2F.3. Свечи сжаты втрое, а объём сдвинут относительно свечей `[ПРОВЕРЕНО]`

**Файл:** `src/components/Simulator.tsx:348–349`

```tsx
<Bar yAxisId="price"  xAxisId="time" dataKey="range"  shape={<CandleShape />} barCategoryGap="25%" />
<Bar yAxisId="volume" xAxisId="time" dataKey="volume" shape={<VolumeBar />}  barCategoryGap="25%" />
```

**Причина.** Обе серии объявлены на **одной оси X** (`xAxisId="time"`). Recharts группирует бары, объявленные на одной оси, и делит полосу категории между ними: свеча получает **левую половину** полосы, объём — **правую**. Отсюда два симптома.

**Замеры в рабочем приложении (3 свечи, поле 530 px):**
```
шаг между свечами:  135 px
ширина свечи:         19 px        ← 14 % от полосы
пустой зазор после:  116 px
свечи: x = 40, 175, 310
объём:  x = 75, 210, 345           ← сдвинут на +35 px (ровно полполосы)
```

То есть **объём нарисован не под свечами, а между ними** — это видно на скриншоте: зелёный столбец объёма стоит правее своей свечи.

**Замеры вариантов (временный роут, DOM-замеры, 8 свечей, поле 530 px):**

| Вариант | Ширина свечи | Зазор после | Смещение объёма |
|---|---|---|---|
| **A** — обе серии на `xAxisId="time"` (сейчас) | 32 px | 104 px | **+56 px** ❌ |
| **B** — объём на отдельной скрытой оси X | **67 px** | 68 px | **0** ✅ |
| **C** — B + явный `barSize={14}` | **9 px** | 126 px | 0 ❌ |
| **D** — B + `barCategoryGap="10%"` + тело 0.78 | **31 px** | 20 px | 4 px ✅ |
| **E** — B + `barCategoryGap="25%"` + тело 0.62 | 25 px | 25 px | 0 ✅ |

**Вывод:** отдельная скрытая ось X для объёма даёт свечу **вдвое шире** и **выравнивает объём точно под свечами**. Вариант D ближе всего к TradingView (свеча занимает ~60 % полосы, зазор виден).

**Внимание:** `barSize` задавать **не надо** — вариант C показал, что явный `barSize` вместе со второй осью даёт свечу 9 px вместо 67 px.

**Что сделать**
```tsx
<XAxis xAxisId="time" dataKey="time" … />
<XAxis xAxisId="volumeTime" dataKey="time" hide />
…
<Bar yAxisId="price"  xAxisId="time"      dataKey="range"  shape={<CandleShape />} barCategoryGap="10%" />
<Bar yAxisId="volume" xAxisId="volumeTime" dataKey="volume" shape={<VolumeBar />}  barCategoryGap="10%" />
```
- коэффициент ширины тела в `CandleShape` поднять с `0.62` до `0.75–0.8`;
- `barCategoryGap` — `10 %` (сейчас `25 %`);
- `barSize` не задавать.

**Критерий приёмки**
- Ширина свечи ≥ 55 % шага между свечами (сейчас 14 %).
- Столбцы объёма **ровно под** свечами (смещение 0 px).
- При 8 свечах в графике шириной ~530 px свеча шириной ~30 px, зазор ~20 px.

### 2F.4. Плейсхолдер Stop-loss читается как «купить по X, продать по Y» `[ПРОВЕРЕНО]`

**Файл:** `src/components/Simulator.tsx:388`

```tsx
placeholder={`Buy ${Number((currentPrice * 0.98).toFixed(2))} / Sell ${Number((currentPrice * 1.02).toFixed(2))}`}
```

**Что показывает (реальный прогон, цена $65 496.98):**
```
Buy 64187.04 / Sell 66806.92
```

**Математика верна** — это уровни **стоп-лосса**, а не цены входа: для Buy стоп ниже входа (−2 %), для Sell стоп выше входа (+2 %). Проверка на сервере это подтверждает (`place_trade` отвергает стоп не с той стороны).

**Но формулировка вводит в заблуждение:** «продать дороже, чем купить» читается как пара цен входа — то есть как инструкция «продай по 66 806, купи по 64 187». В приложении, которое учит риск-менеджменту, такая подсказка опасна: новичок может решить, что Sell — это «продать дороже», а не «открыть шорт со стопом выше».

**Что сделать** — сделать явным, что это стопы:
- вариант А: `стоп Buy: 64 187,04 (ниже входа) · стоп Sell: 66 806,92 (выше входа)`;
- вариант Б (короче): `Stop ≤ 64 187,04 (Buy) · ≥ 66 806,92 (Sell)`;
- вариант В: оставить только один уровень — `стоп для Buy: 64 187,04`, а для Sell показать подсказку при наведении.

Дополнительно: формат чисел в плейсхолдере — с разделителем тысяч (сейчас `64187.04`, а в метриках `$65,496.98` — разнобой, см. 2C.5).

### 3.12. Порог «крупной позиции» не зависит от актива `[КОД]`
